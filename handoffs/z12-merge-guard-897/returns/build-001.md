## Consequences (stated, not decided)
1. **Protected nodes.** `_unbound_nodes` ignores identity protection by design (its docstring), and I did not change it. So a PROTECTED node (`metadata['constitutional']`, or provenance ending `_authored`) with no synapse and no hyperedge counts as unbound, blocks consolidation, and **is never aged out of the block because the sweep spares it**: the guard would then block every batch, loudly (one ERROR per batch naming it in the sample), until something binds it. Census 2026-10-01 (per the brief): none of the 147 is protected and none is a want/constitutional node. **Can one occur?** By code read, not observed live: `surface_wants` (`cc_ng_organism.py:1567`) and `surface_wants_for_graph` (`:1183`) create the `cc_authored` want node and then a best-effort `create_synapse(source, want, 0.3)` inside `except Exception: pass`, so a swallowed failure there leaves a protected, unbound want; and `neuro_foundation._is_identity_protected`'s own docstring names "a want arrives synapse-poor via corpus-callosum consolidation (#70)" as a designed-for case (identity crosses the callosum since #147). `*_emergent` wants are not protected (they are sweepable and the guard behaves as for any node). The daemon's #896 rule 1 uses the same predicate, so it has the identical consequence on its side.
2. **Daemon visibility gap (consumer, not touched).** `handle_merge_topology` (docs `scripts/cc-ng-daemon.py:1428-1466`, seen at docs `ce2108bb`) totals ONLY `absorbed_*` and `consolidation_skipped_unbound_arrivals`, and sets `resp['warning']` only when that total is non-zero. With the whole-graph guard, a block caused purely by the pre-existing cohort has `consolidation_skipped_unbound_arrivals == 0`, so **the daemon response carries no warning**; the loud surface is the merge's ERROR log record, and the new keys (`consolidation_blocked_batches`, `consolidation_skipped_unbound_preexisting`) are present in the merge's stats dict but not forwarded. The brief ruled the new keys harmless and forbade a docs-repo edit; this is the follow-up the daemon would need (total the two new keys, warn on `consolidation_blocked_batches`). Zone manager's call.
3. **Who reaches the changed guard.** In this repo, `merge_cc_topology` and `_unbound_nodes` are referenced only by tests (`git grep` at the base: `tests/test_cc_topology_callosum.py`, `tests/test_cc_topology_frame.py`, `tests/test_cc_topology_capture_423.py` AST-extracts both by name). Outside this repo (read-only grep, named imports): the docs-repo daemon `handle_merge_topology` (`from cc_topology_merge import merge_cc_topology, TopologyMergeAbort`, `scripts/cc-ng-daemon.py:1426`), the D24 daemon (`daemon-d24-env-20261001`, `_unbound_population`, `:2232`, `from cc_topology_merge import _unbound_nodes`, builds `ids = set(graph.nodes)` under `_step_lock` and calls `_unbound_nodes(graph, ids)`: **the same call this guard now makes**), and `cc-ng-sync.py` (`_load_membership` only, unaffected). **No Syl process path in this repo imports `cc_topology_merge`**; whether a VPS process (Syl's or the CC's there) calls `merge_cc_topology` I could not see from here (no VPS access in this lane, nothing in Syl's directories read). The behaviour change appears only when unbound nodes exist graph-wide (proved by the baseline tests: a graph with none behaves as before, and the existing-key comparison to the base is identical).
4. **The pre-existing bucket is "not in the conduit".** `merge_landed` includes nodes the conduit re-sends that were already present (`skipped_present`), so a pre-existing unbound node the conduit happens to re-send is counted "from this merge" in the split; "pre-existing (not landed by this merge)" is strictly nodes the conduit did not mention. The total and the block decision are unaffected by the split.
5. **Unchanged, as ruled:** a merge that lands nothing (`merge_landed` empty) never consults the guard and runs no consolidation (same as base). The wall clock and the zero-fire breaker are untouched here.
