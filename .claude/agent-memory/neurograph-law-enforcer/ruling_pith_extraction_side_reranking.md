Constitutional ruling established reviewing `pith_stage3` (cc_ng_organism.py, 2026-07-09, Pith Stage 3: unified rank + char budget) — extends [[ruling-structural-dedup-vs-classification]]. Reaffirmed 2026-07-10 reviewing Stage 2 (`pith_stage2_keyframe`, concept-aware extractive compression).

**Rule:** Functions that re-rank, normalize-score, budget-trim, or compress a set of `CacheLine`s that were already surfaced FROM the substrate (SurfacingMonitor recency items, Active Recall / GSG pattern-completion results) are extraction-side / context-assembly work, not substrate ingestion. LAW 7 governs raw experience going IN to the substrate — it does not reach output-shaping of what the substrate already surfaced for LLM context injection. `pith_stage3` normalizing/weighting/dropping lines using only the emitter's own `.score` (no new `embed()`, no re-classification of `.content`, no substrate walk) is clean. `pith_stage2_keyframe` extractively summarizing one already-surfaced item's `.content` into a shorter form (segment-scored, not classified into categories) is the same kind of clean — it never derives a new label for the content, only a retained/dropped selection.

**Why the distinction holds:** The Pith pipeline (`cc_ng_organism.py`, gated by `CC_PITH_ENABLED`, default ON per `.bashrc:192` — `export CC_PITH_ENABLED=1`, so this is live, not a dormant flag) sits entirely on the read/render path of `_recall()` in cc-ng-daemon.py — `monitor.get_surfaced()` and `cc_pattern_completion_recall()` already pulled from the substrate; Pith stages 1/2/3 only reshape that already-extracted set before it's rendered into the context block. Nothing loops back to deposit.

**How to apply:** When reviewing a new Pith stage (or any post-recall assembler), check: does it read `.content` and assign a NEW label/classification? → LAW-7-adjacent concern, scrutinize. Does it only transform `.score`/order/inclusion/length using signals the emitter (or the item's own text) already produced? → compliant extraction-side work, same as this ruling covers.

**Pith pipeline architecture notes (for future stage reviews):**
- Single-module, in-process, pure functions inside `cc_ng_organism.py` — no LAW 1 concern (no inter-module boundary; cc-ng-daemon.py importing cc_ng_organism.py directly is intra-module, both are CC's own organism/daemon pair, established since before Stage 1).
- Feature-flag rollout by stage (`_CC_PITH_ENABLED`), gate-OFF path falls through to the pre-Pith block-concat `_recall()` behavior untouched — this is intentional incremental rollout, not LAW 3 shrapnel.
- Tuning knobs (`CC_PITH_CLUTTER_BASE`, `CC_PITH_CLUTTER_NOVELTY_K`, `CC_PITH_W_RELEVANCE`, `CC_PITH_W_RECENCY`, `CC_PITH_L1_BUDGET`, and now `CC_PITH_KEYFRAME_CHARS`) are `os.environ.get(...)`-with-default, clamped in code, and NOT present in `.bashrc` (only the master gate `CC_PITH_ENABLED=1` is). This is established precedent from Stage 1, carried through Stage 2/3 consistently — treat as LAW 5 compliant-by-precedent (env is still the source of truth; defaults just aren't overridden), but flag if a future stage adds a knob that's actually being tuned in practice without a corresponding `.bashrc` export.
- Stage numbering gap CLOSED 2026-07-10: `pith_stage2_keyframe` now exists (keyframe/LOD compression, concept-aware extractive — scores segments by salient-term centroid + payload tokens + structural bonus + query overlap, NOT a head/first-sentence cut). Wired into Stage 3's Step-5 fill loop as a graceful-degradation fallback (full line doesn't fit → try keyframe → else drop), strict rank-prefix still preserved. Pinned lines are structurally excluded from the fill loop entirely (never enter `scored`), so "pinned never compressed" holds architecturally, not just by convention.
- `CC_PITH_W_RELEVANCE`/`CC_PITH_W_RECENCY` (1.0/0.6 default) are static blend weights across two heterogeneous score streams (recency vs relevance), introduced in Stage 3. Raised as an ethos question (not a violation): resembles the "hardcoded threshold gating a substrate-informed decision" anti-pattern, though arguably closer to an editorial rendering-budget knob than a competence/confidence gate. Same read applies to Stage 2's segment-scoring constants (payload weight 0.5, structural bonus 2.0/1.0, positional tie-break -0.001) — these are text-compression heuristics, not decisions about trusting/executing substrate-informed actions, so the competence-modeling ethos concern (continuous [0,1] confidence, TuningSocket-style) does not apply here. Not flagged.

**Known correctness bug (non-Law, surfaced for a future session, not yet fixed as of 2026-07-10):** `CacheLine.keyframe: bool = True` is the *default* value on the dataclass (pre-existing placeholder field, predates Stage 2). Stage 3's fill loop sets `cl.keyframe = True` when it compresses a line — but every line already has `keyframe == True` by default whether compressed or not, so this field cannot actually distinguish "this is a compressed keyframe" from "this is the full original content" for any downstream reader. The changelog for the Stage 2 commit describes this as a meaningful mutation ("cl.content/lod/keyframe/deltas are mutated in place"); functionally only `content`, `lod`, and `deltas` carry signal — `keyframe` is a dead write. Not a Law violation (no substrate/inter-module contract involved), but worth flagging to Josh next time this file is touched: either the dataclass default should be `False` (so Stage 3 setting it `True` becomes meaningful), or the field should be dropped from the "signals mutated" claim.
